# CCU Planner review

Reviewed: `~/Documents/GitHub/ccu-planner` at `ad0e2dc` (main) and the build conversation (18–19 Nov).
Read-only. I did not read `.local/`, start any server, or make any network request. Nothing was run
(no tests, no build), so every claim below comes from reading code and the transcript.
Effort: S = up to half a day, M = one to two days, L = several days.

The pattern behind most findings: the planner's answers were right, but the app shows the result and
not the reason. Each time the user needed the reason, the assistant produced it by hand with the CLI,
a scratch copy of the data and a what-if run. Those hand-made answers are the feature list.

---

## 1. Improvements (product and logic), ranked by value

### 1.1 The app cannot refresh its own data (L)
- **What:** Syncing exists only as a CLI (`scripts/sync.mjs`). The app's only hint is the text
  "run npm run sync in the ccu-planner folder, then press Reload data" (`src/logic/describe.mjs:202`),
  and the Reload button only shows when there is nothing to buy (`app/src/lib/TodayPage.svelte:57-59`).
- **Evidence:** The user asked for a sync four times in two days: "can you now resync the store",
  "yep now quick reload the hangar", "okay so today new day at iae", "bought it, reload the hangar".
  They also asked for a button on day one: "there should be maybe a update store button".
- **Change:** A "Sync" control in the top bar, always visible, with two actions: Store (about 4.5 min,
  261 requests, show progress "upgrades 120/243") and Hangar (seconds, incremental). After a purchase
  link is clicked, offer "Bought it? Refresh hangar". See 2.1 for how to do this without Node.

### 1.2 Explain why a step is in the plan when goals share CCUs (M)
- **What:** A step can exist only because another goal took the owned CCUs this goal would have used.
  The app shows the step but not that dependency.
- **Evidence:** "interesting ccugame doesnt recommend that ccu". The answer needed a scratch copy
  with the Liberator goal removed: without Liberator, the $5 Guardian step drops out. Same on day
  one: Galaxy cost $60 instead of $50 because 600i Explorer had priority, and Ironclad showed $260
  where it would cost $30 alone.
- **Change:** For every goal compute "cost alone" (one extra `searchRoutes` with no exclusions; the
  code already does this for accepted goals in `proposeChain`, `src/logic/chains.mjs:661-678`, but
  only for copies reserved by accepted goals, and it prints chain ids). Show on the goal:
  "$265 in the shared plan · $230 on its own · Liberator uses 2 CCUs this goal would use". On a
  buy-now step show "Needed because Liberator uses your M2 Hercules → Liberator CCU". Extend
  `potential` to draft goals, using `planGoals` exclusions instead of `reservations`.

### 1.3 Say what changed since the last sync (M)
- **What:** The total for all goals is one number with no history (`app/src/lib/GoalsPage.svelte:72`).
- **Evidence:** After the Prospector price rise the shared total went from $855 to $1070. The
  assistant explained it in chat; the app showed only the new number. `recordSeen`
  (`chains.mjs:250-264`) already stores the last proposal per goal, but only the CLI `refresh` uses it.
- **Change:** After each sync store a snapshot (per goal: cash, route signature; plus the offer diff
  that `sync.mjs:90-101` already writes to `offer-history.jsonl`). Show a "Since yesterday" panel on
  Today: "Total +$215. Prospector went from $155 to $175: 3 goals lost their cheap path
  (Orion +$90, Carrack +$80, …). New Warbonds on your routes: Scorpius Antares → Guardian $5."

### 1.4 What-if, without touching real data (M)
- **What:** Every "does this really make sense" question was answered by copying the data folder and
  re-planning: without a goal, with a price change simulated, with 0/1/2 copies bought.
- **Evidence:** "and does buying the ccu with the prospector really make sense" led to a table of
  buy 0/1/2 copies; "can you also make a chain to the liberator" led to a before/after table per goal
  ("So the Liberator really adds $215, not $90").
- **Change:** The state is already pure (`applyAction`, `withDocs` in `app/src/lib/view/derive.mjs:17`),
  so a what-if is `withDocs(app, editedPlans, editedOverrides)` held in memory and never saved. Offer
  three entry points: "Preview" when adding a goal (shows the effect on the other goals before
  saving), "Without this goal" on a goal, and "If I buy this today" on a step.

### 1.5 Urgency of a Warbond is always "today" (M)
- **What:** Every Warbond on a route is "Buy now" (`splitRoute`, `chains.mjs:204`), and Today leads
  with "Your next move: buy N upgrades today" (`describe.mjs:207`).
- **Evidence:** The Phoenix → Galaxy Warbond showed as "buy today" for two days while the Discord
  said "this is going to be available for a few weeks". The assistant told the user to ignore it
  three times.
- **Change:** Split buy-now into "Buy today" and "On sale, no rush". Inputs the app already has:
  first-seen date per offer (`offer-history.jsonl`), the sale event's end date (`sale-events.json`),
  the SKU's `limitedTimeOffer` flag that `getShipDetails` already fetches (`src/rsi.mjs:27`). Let the
  user mark an offer "runs until <date>". Show "on sale since 17 Nov · IAE ends 2 Dec".

### 1.6 Say how many copies to buy, and how to pay (S)
- **Evidence:** "Only one time that warbond?"; "Buy only one copy, even though three goals flag it";
  "and prospector to srv with store credit".
- **Change:** Today's buy list groups by pair across goals: "Scorpius Antares → Guardian · buy 1 ·
  $5 · cash only (Warbond) · for Orion". For Standard steps: "store credit works". Also state the
  negative: "No other goal needs a copy". Today's rows are keyed per goal (`TodayPage.svelte:71`), so
  the same pair for two goals shows as two rows with no count.

### 1.7 Compare with CCU Game inside the app (M)
- **Evidence:** Three exports were dropped into the chat ("compare the results with the results of the
  ccugame", "interesting the ccugame doesnt tell me to buy anything", the 19 Nov file). Each time the
  assistant built a per-goal table by hand. `src/logic/ccugame.mjs` already parses the file, but only
  name, start and target.
- **Change:** In "Import from CCU Game" add a "Compare" result: per chain, CCU Game's cost against
  the planner's, goals that exist only on one side ("Liberator is not in CCU Game"), and different
  starts ("CCU Game starts Orion from a store Pulse without LTI").

### 1.8 Price-lock advice needs the bet spelled out (S)
- **Evidence:** "Why does Oiron say buy 1 today" then "But I have already a orion ccu". The cover
  logic was added afterwards (`lockCover`, `chains.mjs:589-625`), but a lock step still only says
  "This ship is a concept; its price usually rises when it becomes flyable" (`describe.mjs:135`).
- **Change:** On a lock step show the trade: "Buy now for $50, or wait: if Orion rises by $X you pay
  $X more." Give the goal's lock setting a one-click "Don't lock this goal" next to the step, not
  only in the folded Settings.

### 1.9 Daily tips checker (M)
- **Evidence:** The user pasted the CCU Game Discord's daily post four times and asked what it means
  for them. Each answer was the same lookup: is this pair on any of my routes, do I already own it,
  would it make a goal cheaper.
- **Change:** A "Check an offer" box on Store: pick from and to (or paste text and match ship names),
  and get "you own 2 · no goal uses it · would not make any goal cheaper" or "Orion gets $15 cheaper".
  The exact check exists in `wanted.mjs` (add the edge, re-plan).

### 1.10 "What would make it cheaper" is too slow to use (M)
- **Evidence:** "I started a slower check of which offers would help each goal, but it took more than
  2 minutes, so I stopped it" (10 goals). In the app it is behind a fold and lazy
  (`GoalDetail.svelte:56-58`), and it runs on the UI thread.
- **Change:** Run it in a Web Worker with progress and a cancel button; cache per data set on disk.
  Cap the candidate pairs per goal.

### 1.11 Two data folders (S)
- **Evidence:** "the native app looks in a different folder … that doesn't exist on this Mac". The user
  has been using the Vite dev server on a port, not the desktop app. The CLI defaults to
  `<repo>/.local/data`, the app to `~/Library/Application Support/com.ccuplanner.desktop/data`.
- **Change:** One folder. Make the CLI default to the app's folder (`src/data.mjs`, `DATA_DIR`), keep
  `CCU_DATA` as override, and drop the import screen for the normal path.

### 1.12 Smaller gaps
- **Buy links don't preselect ships (S):** `LINKS.upgradePreselect` is `null`
  (`src/logic/links.mjs:9`), so every "Buy on RSI" opens the bare upgrade page. Evidence: "give me the
  link to what to buy". Until a preselect URL is verified, show copyable "From: … / To: … / Edition:
  Warbond" next to the button.
- **Store credit is typed in by hand (S):** `chain credit 50`. The catalog query already returns
  account credit context; show last-synced credit and let the user confirm it.
- **Buyback is synced but unused (M):** README lists it under "Not yet". Buyback CCUs are often the
  cheapest bridges.
- **Token shortage (S):** The assistant worked out "10 tokens, 9 used, UTV free" by hand. `TokenPanel`
  could show the table "token → goal" and a warning when the next goal has none.

## 2. Public release

### 2.1 Blocker: the app needs a Node checkout, Playwright and Chrome to get data (L)
- `README.md` "Desktop app": "It never talks to RSI: the CLI sync above is the only RSI client".
  Login is `chromium.launchPersistentContext(PROFILE_DIR, { channel: 'chrome' … })`
  (`src/session.mjs:22`), stored under the repo (`src/session.mjs:10-11`).
- **Needed:** Login in a Tauri webview window on the RSI origin, read the cookies and CSRF token from
  it, and do the sync in Rust (`reqwest`) or keep `src/rsi.mjs` as a bundled Node sidecar. The Rust
  route avoids shipping Node and `sharp`. Store the session in the OS keychain, not `session.json`.

### 2.2 Blocker: only USD accounts without tax work (M)
- `scripts/sync.mjs:69-71`: for any other currency `upgradeUsdCents` is left `null` with a console
  warning; `src/logic/mapping.mjs:89` then skips every offer. An EUR account gets an empty planner
  and no error in the app.
- The design spec promises the opposite (`docs/superpowers/specs/2026-11-18-ccu-desktop-app-design.md:190-206`,
  "EUR with VAT"), and the user said "EUR definitly. With VAT btw".
- The fallback named in the comment (`getPrice.nativeAmount`, `sync.mjs:68`) is allowlisted
  (`src/rsi.mjs:9,24`) but never called. `usd()` is hard-coded across `describe.mjs` and the UI.
- **Needed:** Plan in USD cents (native), display in account currency with tax; one `money()`
  formatter fed by `catalog.app.pricing`. Test on a real EUR account before telling friends.

### 2.3 RSI terms and request behaviour (M, plus a decision)
- The client is careful: GET allowlist and query allowlist, mutations refused (`src/rsi.mjs:8-9,131`),
  1 request per second (`rsi.mjs:35,63`), one retry on 429 (`rsi.mjs:94-99`).
- Risks for a public tool: it automates a logged-in account on undocumented endpoints; it rewrites the
  user agent to hide headless Chrome (`src/session.mjs:31`); a full store sync is about 261 requests
  per user per day during a sale; a single 429 retry and then a hard error with no resume
  (`sync.mjs:80-104` restarts from ship 1).
- **Needed:** Read RSI's ToS on automated access and decide. Remove the user-agent rewrite and send an
  honest client name. Add exponential backoff, resume from the last synced source ship, and a floor on
  sync frequency (for example no full store sync within an hour). Consider syncing only source ships
  that can reach a goal (the reachability code exists in `chains.mjs:469-487`) — this would cut
  requests a lot. A shared, account-independent store feed would remove most per-user requests, since
  Standard and Warbond offers are the same for everyone.
- Add a "not affiliated with Cloud Imperium / RSI" notice and check the fan-site rules for the name
  and ship pictures. Pictures are downloaded per user (`scripts/sync-images.mjs`) and not bundled;
  keep it that way.

### 2.4 Session and secrets (S–M)
- `session.json` holds RSI cookies in plain text at mode 600 (`session.mjs:37-40`); the Chrome profile
  in `.local/profile` holds the full login. Both sit inside the git checkout, protected only by
  `.gitignore`. `scripts/capture.mjs` writes recorded traffic to `.local/capture`.
- **Needed:** Move session data out of the repo to the app data folder or keychain; add a "Sign out
  and delete session" action; never log cookie values (currently only method, status and path are
  logged, `rsi.mjs:83` — good).

### 2.5 Packaging, signing, updates (M)
- `app/src-tauri/tauri.conf.json`: `"targets": ["app"]` only (no dmg, no Windows installer although
  the user asked for "Mac and Windows later linux"); no updater plugin; no signing or notarisation
  config; version `0.1.0` in two places; identifier `com.ccuplanner.desktop` is a placeholder domain.
- `app/package.json` requires Node 26 and npm 11 exactly; root `package.json` has no `engines`.
- **Needed:** dmg + NSIS targets, Apple Developer ID signing and notarisation, Windows signing (or
  accept SmartScreen warnings), `tauri-plugin-updater` with a signed release feed, a real identifier.

### 2.6 Onboarding (M)
- First run asks for "the data folder of an existing CCU planner checkout" with the developer's own
  path as default (`app/src/lib/ImportScreen.svelte:6,29`). A new user has no such folder.
- The explainer is three sentences (`app/src/lib/view/firstRun.mjs:2-6`). It does not cover LTI
  tokens, Warbond vs Standard, store credit, melting, or why "today" and "if the sales come back"
  differ — the exact points the user called the old tool's biggest pain.
- **Needed:** First run = sign in → sync with progress → "pick your first goal". A glossary reachable
  from every term (hover or "?"), and a sample data set so people can look around before signing in.

### 2.7 Errors, privacy, docs, licence, CI
- **Errors (S):** Sync errors are thrown strings from the CLI; the app shows one notice line
  (`Shell.svelte:62-64`). A parse change on RSI's hangar HTML (`src/parse.mjs`) would produce an empty
  or partial hangar. Add a sanity check (pledge count dropped by more than half → refuse to overwrite)
  and a readable "RSI changed something" message.
- **Hand-reviewed mapping (M):** `src/logic/aliases.json` maps hangar CCU names to ships for one
  hangar. Other users will hit unmapped CCUs; the "needs review" list exists only in
  `scripts/plan.mjs --status`. Surface it in the Hangar with a way to fix a mapping.
- **Privacy (S):** All data is local, which is the selling point; write it down (what is stored,
  where, how to delete). No telemetry exists; keep it that way or make it opt-in.
- **Licence (S):** No `LICENSE` file; both `package.json` files are `"private": true`. Pick one
  (`sharp`, `cheerio`, `echarts`, Inter are all permissive).
- **Docs (S):** `README.md` still opens with "CCU planner (prototype) … This first part is a read-only
  RSI client" and is CLI-first. Split into a user guide and a developer guide.
  `docs/superpowers/plans|specs` are build artefacts; keep them out of a public repo or mark them.
- **CI (S):** No `.github/`, no `test` script in the root `package.json` (tests run only as
  `node --test test/`), no lint, no type check, no Rust `cargo test`/`clippy` run. Add one workflow:
  `node --test`, `vite build`, `cargo test`.

## 3. Maintainability

### 3.1 One "route advice" object instead of six re-derivations (M) — highest value
- **What:** The same sequence — `lockDecision` → `splitRoute` → build the skip list → `expectedChanges`
  / `buyBeforeTexts` — is written out in:
  `src/logic/journey.mjs:34-48`, `src/logic/decision.mjs:86-92`, `app/src/lib/view/today.mjs:71-73`,
  `app/src/lib/view/steps.mjs:10`, `app/src/lib/Steps.svelte:22`, `src/logic/melt.mjs:134-146`,
  and three times in `scripts/chain.mjs:103-109,163-175,362`.
- **Why:** The file header admits it: "Mirrors groupSteps … and buyBeforeTexts" (`journey.mjs:5-6`).
  Yesterday's last three commits (`de517e7`, `cf260b3`, `bfbfd75`) all fixed pages disagreeing about
  the same warning; the review found "one page could show the warning while another hides it". The
  fix added a `ctx.route` escape hatch (`chains.mjs:176-180`) so callers that pass a partial route
  still get the full-route answer, which is a workaround for callers slicing the route themselves
  (`decision.mjs:91`).
- **Refactor:** `routeAdvice(session, chainId, route)` in a new `src/logic/advice.mjs` returning
  `{ dec, split, skip, alerts: [{ step, reason, saves, text }], later }`. It handles `finish` mode
  itself (today the same literal `{ reason: null, cover: null, … }` is duplicated at
  `decision.mjs:86` and `journey.mjs:34`). `journey`, `decisionGraph`, `todayView`, `groupSteps`,
  `meltPlan` and the CLI only format it. `journey.mjs:46-48` currently calls `expectedChanges` twice
  and zips texts to steps by array index; that goes away.

### 3.2 Split `chains.mjs` (796 lines, five jobs) (M)
- State and CRUD: `newState`, `addChain`, `setMode/Lock/Objective`, `acceptRoute`, `releaseChain`,
  `evaluateAccepted`, `diffRoutes` (lines 18-75, 190-228, 682-770) → `goals.mjs`.
- Shared planning: `goalStarts`, `chooseGoalOrder`, `planGoals`, `proposeChain`, `proposeFleet`
  (285-540, 648-680, 772-796) → `sharedPlan.mjs`.
- Price-change alerts and waiting penalty (77-188) → `priceChange.mjs`.
- Lock and cover (195-244, 542-646) → `lock.mjs`.
- `planGoals` itself is 113 lines with four closures (`relevant`, `planOne`, `searchOne`, and the
  level loop, 427-540); pull the reuse cache (`found`, 488-512) into its own small unit with the
  invariant from the comment as a test.

### 3.3 Replace nine ad-hoc memos with one planning session (M)
- **What:** `waitMemo` (`chains.mjs:77`), `planMemo` (`:414`), `coverMemo` (`:542`), `graphOf`
  (`melt.mjs:127`), `wantedMemos` (`wanted.mjs:179`), `memos` (`decision.mjs:205`), `memos`
  (`app/src/lib/view/subgraph.mjs:10`), `memos` (`view/hangar.mjs:125`), `todayMemos`
  (`view/today.mjs:10`), plus one inside a component (`WarbondsTab.svelte:6-16`). Each has its own key
  (some `plans.rev|overrides.rev|events.rev|day`, some object identity, one a `JSON.stringify` of
  every goal including all accepted routes on every call, `chains.mjs:431-434`) and its own size limit
  (4, 6, 8).
- **Why:** Correctness depends on every key listing every input. `lockCover` already needs a
  `lockKey` inside its memo because the answer depends on which goals lock (`chains.mjs:597-612`).
  `todayView` calls `proposeChain` per goal, then `journey` (which calls `lockDecision`), then
  `lockDecision` again (`today.mjs:39-71`); it is fast only because of the hidden memos.
- **Refactor:** Build one `PlanSession` per (data, plans rev, overrides rev, events rev, day) in
  `withDocs` (`view/derive.mjs:17`) with lazy fields: `shared` (planGoals), `route(chainId)`,
  `advice(chainId)`, `cover`, `wanted(chainId)`. When a document changes, a new session replaces the
  old one and everything is dropped together. The module-level WeakMaps go away.

### 3.4 The graph is a `Map` with extra properties (S)
- `buildGraph` sets `out.lti` and `out.concept` on the Map (`planner.mjs`, end of `buildGraph`).
  Every function that copies the graph must remember them: `expectedGraph` (`chains.mjs:83-84`),
  `withStandard` (`chains.mjs:90-92`). Forgetting one silently disables token starts or the concept
  tie-break. Make it `{ edges: Map, lti, concept }` with a `withEdge()` helper.

### 3.5 Two storage back ends that must stay identical (M)
- `app/src-tauri/src/store.rs` (602 lines) and `app/vite-dev-data.js` (144 lines) implement the same
  load, revisioned save, and import allowlist. Tests cover only the JS one
  (`test/view/dev-store.test.mjs`). The user runs the JS one daily; the Rust one is the product and
  has never held real data (see 1.11).
- **Refactor:** Either make the Rust side a thin "read file / write file with rev check" and keep the
  allowlist and shape in JS, or add one shared fixture folder that both a Node test and a `cargo test`
  load and compare.

### 3.6 Names: "chain" in code, "goal" in the UI (S–M)
- State is `plans.chains`, ids are `c1…`, functions are `addChain`, `proposeChain`; the UI and README
  say "goal". The ids leak to the user: "reserved by c3" (`decision.mjs:135`), "$X less if c1, c4
  released" (`GoalDetail.svelte:169`), "CCU 123 (45->67) no longer in hangar" and "LTI token 123
  (ship 45)" with raw ship ids (`chains.mjs:707-717`, shown via `GoalDetail.svelte:124`).
- `evaluateAccepted` returns issues as a mix of strings and objects (`chains.mjs:688`), hence the
  `issueText` helper. Return objects `{ kind, from, to, … }` only and let `describe.mjs` word them.
- `describe.mjs` carries CLI and app variants of the same text (`MELT_IDLE` / `MELT_IDLE_APP`,
  `meltPlanLines` / `meltPlanLinesApp`, lines 27-53). Once the app can sync, freeze the CLI at
  developer wording and stop mirroring.

### 3.7 Tests (S–M)
- 26 files, flat, named by feature; a brute-force comparison for the planner. Good.
- Gaps: no `npm test`; no test that the pages agree with each other (the bug class in 3.1) — add one
  property test: for each fixture goal, Today, journey, decision graph and CLI text give the same set
  of buy-now steps and alerts. No UI test at all: every UI check in the transcript was the assistant
  clicking through a browser on a copy of real data. `vite-dev-data.js` makes a Playwright smoke test
  on `test/fixtures` cheap (open each section, open the Advanced menu, click each item — that test
  would have caught the hidden menu).
- `planGoals` has a test-only `_internal` option that bypasses the memo (`chains.mjs:427-429`); with
  3.3 it becomes an ordinary parameter of the session.

### 3.8 Dead and legacy code (S)
- `base` → `start` migration for a two-day-old, single-user data file: `startOf` fallback
  (`chains.mjs:30`), `migrateGoals` (`:48-67`), the "older documents" token repair in `planGoals`
  (`:450-457`), and the migration call on every `withDocs` (`derive.mjs:18`). Migrate the one file
  once and delete.
- `scripts/capture.mjs` (138 lines, endpoint discovery) and `scripts/plan.mjs` (single-route CLI that
  predates goals): move to `tools/` or delete. `getPrice` query is allowlisted but unused
  (`rsi.mjs:9,24`) until 2.2 is done.
- `app/src/lib/Steps.svelte` + `view/steps.mjs` are only used by the Advanced plan explorer
  (`PlanExplorer.svelte:6`) and are a second step renderer next to `JourneyStep`; fold into one.
- One-line re-export files: `view/format.mjs` (1 line), `view/quickSearch.mjs` (2), `view/goalLabel.mjs` (3).

## 4. Interface

All grounded in what the user typed; I could not open the app.

### 4.1 Today should answer "what should I buy today" completely (M)
- **Evidence:** That question was asked in chat at least seven times ("so what warbonds would I buy
  today basically?", "okay so nothing to buy today", "which upgrades hould I buy again", "so what
  today?", "ahh oaky so what should I buy today"). The app's Today page existed for most of them.
- **Why the page did not settle it:** the buy list is hidden behind a "Show me" button
  (`TodayPage.svelte:63,68`); each row has no reason unless it is a lock (`:77`); no count, no payment
  method; Warbonds that run for weeks sit in the same list as one-day offers.
- **Change:** Show the list open by default as three groups:
  1. **Buy today** — "Scorpius Antares → Guardian · Warbond $5 · cash only · buy 1 · for Orion ·
     new today, Standard is $20".
  2. **On sale, no rush** — with "on sale since …, likely until …".
  3. **Optional** — locks and bets, each with the trade in one line (see 1.8).
  End with an explicit "Nothing else: no other goal needs a purchase today."

### 4.2 A sync control and data age that is always visible (S for the UI, see 1.1)
- The data age is small grey text in the bar and hidden under 1024 px (`Shell.svelte:59,113`). Put
  "Store: today 16:38 · Hangar: today 16:50 · [Sync]" there as a real control and turn it amber when
  the store data is from an earlier day during a sale event.

### 4.3 Show the shared-plan effect where goals are listed (M, with 1.2)
- **Evidence:** "'Plan all goals together' its unclear what that button does" and "shouldnt this be
  the default?"; later the Liberator question.
- **Change:** Goal cards show "$265 (alone $230)". The header shows "All goals: $1070 · +$215 since
  yesterday" as a link to the change panel (1.3). Adding a goal shows the preview from 1.4 before
  saving: "Liberator: $90. Other goals get $125 more expensive."

### 4.4 Priority needs a visible meaning (S)
- Priority decides who gets shared CCUs first, which moved Ironclad from $30 to $260. In the UI it
  is a dropdown in folded Settings (`describe.mjs:166`). Show goals in planning order with drag to
  reorder and the cost effect of a move.

### 4.5 Don't show internal ids or CLI words (S)
- See 3.6: "c1", copy ids, ship ids in the accepted-route issues, and status words `ok` / `repriced`
  / `blocked` printed raw (`GoalDetail.svelte:122`). Also "Accepted route" / "Release" / "Accept all
  plans": the user never asked what accepting is for, and the assistant never explained it in the
  app's terms. Either explain in one line ("Accepting holds these CCUs for this goal") or hide
  accepting until the user wants to pin a plan.

### 4.6 The "three money figures" still need the user's one sentence (S)
- **Evidence:** The stated pain: "the difference between long term saving and current highest savings
  was really hard to grasp". The figures exist (`describe.mjs:148-152`), but "If the sales come back"
