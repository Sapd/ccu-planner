## Rulings (mine; the user can overturn)
- **No Rust port of the RSI client in this round.** The app runs the existing Node sync (dev
  server: child process; Tauri: shell command to the bundled scripts).
  - Why: the user's daily use is the dev server, and a Rust port is L-sized.
  - Cost if wrong: a public build still needs Node; this is listed as an open release item.
- **EUR/VAT: no live verification.** The user's account is USD. Formatting goes through one
  `money()` function, and non-USD accounts get a clear error instead of silent empty data.
  Converting with `getPrice` stays open until someone with an EUR account can test it.
- **Signing/notarisation, updater feed, licence choice, public name/identifier:** prepared as config
  with placeholders where they need the user's accounts or choice.
- **Base→start migration:** migrate the real `plans.json` only through the app's normal load/save on
  the next write. Delete the migration code only if `plans.json` has no `base` field (check
  read-only); otherwise keep it.

## Form of the app (user decision 2026-11-19): keep the desktop app, solve its release problems
This replaces the ruling "no Rust port / app runs the Node sync" above.
- **Login in the app:** a Tauri webview window on robertsspaceindustries.com. The user signs in
  there themselves (the app never sees the password). Session cookies are read from that webview.
  Playwright, headless Chrome and the user-agent rewrite are not needed in the app. The CLI may keep
  its current client for development.
- **Sync without Node:** the RSI client and parsers run inside the app:
  - the JS client, with requests through Rust (tauri-plugin-http or a small Rust command);
  - `cheerio` replaced by DOMParser or a Rust HTML parser;
  - the same read-only allowlist, rate limit, backoff and resume as the CLI;
  - ship pictures loaded from RSI's public URLs and cached, with no `sharp`.
- **Session storage:** the OS keychain (macOS Keychain / Windows Credential Manager), never a file in
  the repo, plus a "Sign out and delete session" action.
- **One data folder:** the app data folder. The CLI uses it by default too.
- **Packaging:**
  - dmg (macOS) and NSIS (Windows) targets, with an AppImage/deb config for Linux;
  - signing and notarisation config with placeholders for the user's Apple Developer ID and Windows
    certificate;
  - tauri-plugin-updater against a GitHub Releases feed (the updater signing key is generated by the
    user; the docs explain how).
- **Rust store:** tests shared with the JS dev store through one fixture folder.

## Phase 7: MCP server (user request 2026-11-19)
Goal: let Claude (or another MCP client) answer the questions from the 18–19 Nov chat directly from
the planner, instead of CLI digging and scratch copies.
- A stdio server in Node (`@modelcontextprotocol/sdk`; check current docs through Context7). It
  reads the same data folder as the app (`CCU_DATA` override), and uses the phase-1 planning
  session and `routeAdvice`.
- Read-only tools:
  - `today` (buy today / no rush / optional, with count and payment);
  - `goals` and `goal` (route, cost alone vs shared, why each step);
  - `changes_since_sync`;
  - `what_if` (in memory: add or remove a goal, buy N copies, a price change);
  - `check_offer` (from, to, price);
  - `compare_ccugame` (path to a Saved Chains file);
  - `hangar_ccus_into` (ship).
- Sync tools:
  - `sync_hangar` and `sync_store`, using the same read-only RSI client as the app;
  - `sync_store` reports progress.
- **Ruling:** tools that change plans (add goal, accept, lock, credit, price override) exist only when
  the server is started with `--allow-writes`, and each writes through the normal revisioned save.
  - Why: a model shouldn't change plans by accident.
  - Cost if wrong: the user starts it with the flag.
- No tool buys, melts, gifts or applies anything on RSI; the server has no such code.
- README section on how to register it in Claude Code (`claude mcp add`). Tests call each tool's
  handler on `test/fixtures`.
